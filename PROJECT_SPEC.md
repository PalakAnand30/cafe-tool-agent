## 1. Goal and success criteria

Fine-tune a small open model with QLoRA so that it acts as a café ordering assistant: it turns customer messages into correct, schema-valid tool calls against a café API, asks for clarification when information is missing, and declines unsupported requests. Prove with a rigorous evaluation that it beats prompting-only baselines, including a much larger prompted model, and serve it cheaply on CPU.

Success criteria:
- Reproducible pipeline: `make data`, Kaggle training, Kaggle GPU eval, `make eval-local`, `make report`, `make serve`.
- Results table comparing 5 systems (Section 6) on a synthetic held-out test set and a human-written test set, with 95% bootstrap confidence intervals on the human set.
- Public artefacts: GitHub repo, Hugging Face dataset, LoRA adapter, merged model, GGUF model, and a live Hugging Face Space demo.

## 4. Café domain

**Menu** (`configs/domain.yaml`): about 25 items across categories `coffee`, `tea`, `cold_drinks`, `bakery`, `sandwiches`.
- Drinks have sizes `small | medium | large` with price per size. Food has no size.
- Each item lists allowed modifiers with price deltas, e.g. `oat_milk`, `soy_milk`, `extra_shot`, `decaf`, `no_sugar`, `vanilla_syrup`, `iced`, `warmed`. Modifiers not in an item's list are unsupported for that item.
- 2–3 items are out of stock (deterministic from config). Include near-duplicate names to create genuine ambiguity (e.g. "latte", "iced latte", "chai latte").

**Tools** (OpenAI-style function schemas, which Qwen's chat template accepts via `tools=`):

| Tool | Arguments | Returns |
| --- | --- | --- |
| `get_menu` | `category?: enum` | items with sizes, prices, modifiers, availability |
| `check_availability` | `item_name: str`, `size?: enum` | `{available: bool, alternatives: [...]}` |
| `create_order` | `customer_name?: str`, `items: [{item_name, size?, quantity: int 1–10, modifiers: [str]}]` | `{order_id: "ORD-12345", total, eta_minutes}` or a structured error |
| `get_order_status` | `order_id: str` (pattern `ORD-\d{5}`) | `{status, eta_minutes}` |
| `cancel_order` | `order_id: str` | `{cancelled: bool, reason?}` |

Backend rules: validate everything; return structured errors (`ITEM_NOT_FOUND`, `OUT_OF_STOCK`, `UNSUPPORTED_MODIFIER`, `SIZE_REQUIRED`, `ORDER_NOT_FOUND`, `CANNOT_CANCEL`). Order state machine `received → preparing → ready → collected`; cancel allowed only before `ready`. Status progression is deterministic (seeded) so evaluation is reproducible. The backend can run in-process (for data validation and eval) or as an HTTP service (for the demo).

**Assistant behaviours** (encode in the system prompt and the data):
1. **Call a tool** when the request is complete.
2. **Clarify** (plain-text question, no tool call) when a required detail is missing or ambiguous: size missing for a sized drink, ambiguous item name, unclear quantity.
3. **Decline** politely with an alternative for off-menu items, unsupported modifiers, or out-of-scope requests (refunds, complaints, weather, unrelated chat).
4. **Recover from tool errors**: after an `OUT_OF_STOCK` or similar error, tell the customer and offer the alternatives the tool returned.
5. Order directly with `create_order`; do not call `check_availability` first unless the customer asks about availability.

## 5. Dataset

**Format**: JSONL, one conversation per line, Hugging Face chat format:
`{"id", "split", "intent", "template_id", "tools": [...], "messages": [{"role": "system"|"user"|"assistant"|"tool", "content", "tool_calls"?, "tool_call_id"?}], "expected_final_state": {...}, "scripted_user_turns": [...]}`

**Generation** (`cafe_agent.data`):
- Python templates per intent, filled by sampling items, sizes, quantities, modifiers and names. Labels (tool calls, arguments, tool results from the real in-process backend, final assistant replies) are produced programmatically so they are correct by construction.
- Assistant final replies come from varied response templates (not an LLM).
- Paraphrase about 30% of user turns with Groq Llama 3.3 70B. Instruct it to keep every item, size, quantity, modifier and name; then **verify** entities survived (string or synonym map match) and reject failures. Log the rejection rate.
- Noise on about 15% of user turns: typos, lowercase, missing punctuation, UK/US spelling, informal phrasing ("lemme get", "cheers").

**Intent mix** (`configs/data.yaml`, adjustable):

| Intent | Share |
| --- | --- |
| Single-item order | 18% |
| Multi-item order with modifiers | 17% |
| Clarification needed | 15% |
| Availability question | 8% |
| Order status | 8% |
| Cancel order | 6% |
| Menu browsing | 6% |
| Unsupported modifier / off-menu item | 10% |
| Tool-error recovery (out of stock etc.) | 6% |
| Out-of-scope / small talk | 6% |

About 25% of conversations are multi-turn (e.g. clarification then completion, order then status, order then cancel).

**Splits and leakage control**:
- Train ~3,500, validation ~300, synthetic test ~400.
- Reserve 20% of templates and a set of (item, modifier) combinations exclusively for the test split.
- Deduplicate by normalised user text across all splits; assert no overlap in tests.

**Validation**: every example must (a) pass schema validation for every tool call, (b) replay against a fresh backend and reproduce the stored tool results and `expected_final_state`, (c) render with the Qwen tokenizer chat template under 1,024 tokens. Write `data/generated/stats.md` with counts per intent, turn lengths, token lengths and paraphrase rejection rate.

**Human test set** (`data/human_test/human_test.jsonl`): 60–100 conversations written by the user, not generated. Build `scripts/annotate_human_test.py`, an interactive CLI where the user types customer messages and selects or types the expected behaviour (tool + arguments, clarify, decline) and expected final state; it validates entries against the schema and backend. Seed the file with 5 examples written by you, clearly marked `"author": "codex_example"`, which are excluded from scoring.

**Publishing**: `scripts/push_dataset.py` pushes train/validation/test (and human test, separately) to `HF_USERNAME/cafe-tool-calls` with a dataset card. Start private; the user makes it public at the end. The Kaggle notebooks load data from this HF dataset.

## 6. Evaluation

**Systems**:

| ID | System | Runs on |
| --- | --- | --- |
| S1 | Qwen2.5-1.5B-Instruct, zero-shot (system prompt + tools) | Kaggle, vLLM |
| S2 | Qwen2.5-1.5B-Instruct, few-shot (same + 4 fixed examples) | Kaggle, vLLM |
| S3 | Llama-3.3-70B via Groq, native tool calling, same system prompt | Local |
| S4 | Fine-tuned LoRA, merged, fp16 | Kaggle, vLLM |
| S5 | Fine-tuned, GGUF Q4_K_M | Local, llama-cpp-python, CPU only |

All systems use the same system prompt and tool schemas from `cafe_agent.prompting`, temperature 0, `max_tokens` 512. All write predictions to `results/predictions/{system}__{split}.jsonl` with one shared pydantic schema. Metrics are computed **locally** by one script from these files, so every system is scored identically.

**Two evaluation modes**:
1. **Turn-level**: for each assistant turn, give the gold history and score the predicted next action.
2. **End-to-end**: run the agent loop against a fresh backend, feeding `scripted_user_turns` in order; success = final backend state equals `expected_final_state` with no extra side effects (no extra orders, no wrong cancellations).

**Metrics**: valid tool-call rate (parses and validates against schema); action accuracy (correct tool vs clarify vs decline); argument exact match and field-level F1 (item, size, quantity, modifiers); clarification precision and recall; decline precision and recall; end-to-end task success; latency p50/p95 (S5 locally on CPU; S3 recorded but flagged as including network time); estimated cost per 1,000 conversations (S3 from Groq's published paid token prices with the date noted; S5 as local compute, stated as an assumption).

**Rigour**: 95% bootstrap confidence intervals (1,000 resamples) for all metrics on the human test set; per-intent breakdown; intent confusion matrix; `results/error_analysis.md` with failure categories and 10 representative failures for S4 vs S2.

**Charts** (`results/charts/`): system comparison bar chart with CI whiskers (human set), per-intent accuracy heatmap, confusion matrix, latency vs accuracy scatter (systems as points), optional ablation curves.

## 7. Training (Kaggle notebook `train_kaggle.ipynb`)

- Self-contained: pinned install cell; `pip install git+https://github.com/<GITHUB_USERNAME>/cafe-tool-agent.git` (repo must be public, or read a `GITHUB_TOKEN` Kaggle secret); load data from HF; read secrets from Kaggle Secrets; log to W&B.
- Model: `Qwen/Qwen2.5-1.5B-Instruct` at the pinned revision, 4-bit NF4 with double quantisation, compute dtype **float16** (T4 has no bf16). Single GPU.
- LoRA: r=16, alpha=32, dropout=0.05, target all linear projections (`q,k,v,o,gate,up,down`).
- Trainer: TRL `SFTTrainer`, lr 2e-4, cosine schedule, warmup 3%, 2–3 epochs (config), max sequence length 1,024, per-device batch 4, grad accumulation 4, gradient checkpointing, eval each half epoch, save best by validation loss.
- **Loss on assistant tokens only**: implement label masking yourself in `cafe_agent.data` (render with the chat template, set non-assistant tokens to -100). Unit-test the masking locally using the tokenizer only.
- Cell parameters at the top for ablations (`LORA_R`, `TRAIN_FRACTION`, `RUN_NAME`) so the user can rerun cheaply; default is one main run.
- Outputs pushed to HF Hub: adapter `HF_USERNAME/cafe-agent-qwen2.5-1.5b-lora`, merged fp16 model `...-merged`, and GGUF `...-gguf` (`Q4_K_M`, built in CPU cells with llama.cpp). Each repo gets a model card with training details and W&B run link.
- Print a final summary cell: train/val loss, runtime, GPU hours used, Hub URLs.
